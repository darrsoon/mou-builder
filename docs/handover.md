## Порядок

1. Открыть доступ новому владельцу к папке «MOU (Prime Bridge)» (`1aj_s4joYlP-8QnEn8fLRTSHdFtjDs2MG`),
   папке «Готовые MOU» (`1-gkMgBa_BQAlRC11tDacdSPElZj9vXiH`) и таблице.
2. Передать владение каждым объектом: правой кнопкой → «Открыть доступ» → у нужного
   человека выбрать «Передать права владельца».
   **Важно:** передать владение можно только внутри одной организации. Если у нового
   владельца почта не на `primebridge.estate`, права владельца Google не отдаст —

   у него и вписать новые ID (п. 4).
3. Договоры, созданные сайтом, лежат в папке «Готовые MOU» и принадлежат тому аккаунту,

### 2. Google Cloud: вход на сайт

Сайт пускает людей внутрь через OAuth-клиент. Клиент прежнего владельца новому
не передаётся — создаётся новый:

1. https://console.cloud.google.com → создать проект.
2. APIs & Services → включить Google Docs API, Google Drive API, Google Sheets API.
3. OAuth consent screen: тип **Internal**, если почта в Google Workspace, иначе
   **External** плюс добавить всех, кто будет пользоваться, в Test users.
4. Credentials → Create credentials → OAuth client ID → Web application.
   - Authorized redirect URI: `https://<адрес сайта>/api/auth/callback/google`
   - для работы на своём компьютере добавить второй: `http://localhost:3000/api/auth/callback/google`
5. Сохранить Client ID и Client secret — они понадобятся в п. 4.

### 4. Vercel: сайт

1. Новый владелец регистрируется на https://vercel.com (удобнее — входом через GitHub).
2. Прежний владелец: проект `mou-builder` → Settings → General → Transfer project,
   выбрать аккаунт нового владельца. Новый владелец подтверждает запрос.
3. После переноса проверить, что проект связан с репозиторием нового владельца:
   Settings → Git. Если связи нет — подключить заново.
4. Settings → Environment Variables. **Старые значения прочитать нельзя**, часть
   нужно задать заново:

| Переменная | Что вписать |
|---|---|
| `GOOGLE_CLIENT_ID` | из нового OAuth-клиента (п. 2) |
| `GOOGLE_CLIENT_SECRET` | из нового OAuth-клиента (п. 2) |
| `GOOGLE_ALLOWED_DOMAIN` | домен почты, которой разрешён вход, например `primebridge.estate`. Пусто — пускает всех |
| `NEXTAUTH_URL` | адрес сайта целиком, например `https://mou-builder.vercel.app` |
| `NEXTAUTH_SECRET` | новая случайная строка: `openssl rand -base64 32` |
| `MOU_SPREADSHEET_ID` | ID таблицы MOU Builder |
| `MOU_OUTPUT_FOLDER_ID` | ID папки «Готовые MOU» |
| `MOU_TEMPLATES` | можно не задавать: список шаблонов живёт в коде, `lib/mou/config.js` |
| `MOU_TEMPLATE_DOC_ID` | не нужна, осталась от версии с одним шаблоном |
| `MOU_PROJECTS_SHEET` `MOU_LISTS_SHEET` `MOU_LOG_SHEET` `MOU_RULES_SHEET` `MOU_AGENTS_SHEET` | названия листов таблицы: `PROJECTS`, `LISTS`, `DRAFTS_LOG`, `RULES`, `AGENTS`. Если не задавать — берутся эти же значения |

5. Deployments → Redeploy, чтобы новые переменные подхватились.
6. Если адрес сайта поменялся: вписать новый `NEXTAUTH_URL` и добавить его redirect URI
   в OAuth-клиент (п. 2.4), иначе вход будет падать с ошибкой `redirect_uri_mismatch`.

### 5. Работа на своём компьютере

Это нужно только тому, кто **меняет код** или **размечает шаблоны** (п. 6). Сайт
работает на Vercel сам, ничей компьютер для этого включённым держать не надо.
Если работа только с текстами договоров в Google Docs — этот пункт можно пропустить.

Дальше по шагам, для macOS. Все команды — в приложении «Терминал»
(Spotlight ⌘+пробел → «Терминал»).

**5.1. Node.js.** Проверить, стоит ли:

```bash
node -v
```

Нужен Node 22.15 или новее: тест маршрутов API пользуется `module.registerHooks`,
на более старых он падает. Проще сразу поставить последнюю LTS.
Если команда не найдена или версия старая — скачать установщик с https://nodejs.org (кнопка LTS) и пройти установку,
потом закрыть и открыть Терминал заново.

**5.2. Git.** Проверить:

```bash
git -v
```

Если не стоит, macOS сам предложит доустановить Command Line Tools — согласиться.

**5.3. Забрать код.**

```bash
cd ~/Desktop
git clone https://github.com/<аккаунт владельца>/mou-builder.git
cd mou-builder
npm install
```

`git clone` попросит войти в GitHub — если репозиторий приватный, вход обязателен
(проще всего поставить `gh` и сделать `gh auth login`, либо создать Personal Access
Token в настройках GitHub и вставить его вместо пароля).
`npm install` качает зависимости, идёт 1–2 минуты, предупреждения в выводе — норма.

**5.4. Свои настройки.** В репозитории лежит пример, с него делается личный файл:

```bash
cp .env.example .env.local
open -e .env.local
```

Вписать те же значения, что на Vercel (п. 4), с двумя отличиями:

- `NEXTAUTH_URL=http://localhost:3000` — для локального запуска;
- `NEXTAUTH_SECRET` — любая длинная случайная строка, можно получить командой
  `openssl rand -base64 32`.

Ещё в `.env.example` нет строки `MOU_AGENTS_SHEET=AGENTS` — если листа с таким
именем в таблице нет, добавить переменную со своим названием.
Файл `.env.local` в репозиторий не попадает (он в `.gitignore`), и это правильно:
в нём секреты.

**5.5. Запуск.**

```bash
npm run dev
```

Открыть http://localhost:3000. Это та же программа, что на сайте, но берёт код
с компьютера: любая правка файла видна в браузере сразу. Останавливается
сочетанием Ctrl+C в Терминале. **Важно:** локальная копия работает с теми же
Google-документами, что и прод — созданные договоры попадут в настоящую папку
и настоящий журнал. Для опытов менять `MOU_OUTPUT_FOLDER_ID` на тестовую папку.

**5.6. Проверки перед тем, как выкладывать.** Три команды, все должны пройти чисто:

```bash
npm test            # тесты: разметка, расчёты, маршруты API
npx next build      # сборка — так же, как её делает Vercel
npm run check:undef # только если менялся серверный код (app/, lib/)
```

Последняя ловит необъявленные переменные: сборка Next их пропускает, и такая
ошибка всплывает уже на проде при создании договора — так однажды и случилось.

**5.7. Выложить изменения.**

```bash
git add -A
git commit -m "что сделано"
git push
```

Пушим прямо в `main` — Vercel подхватывает и выкладывает новую версию сам,
за минуту-две. Отдельных веток и pull request'ов в проекте нет.

### 6. Токен бота для разметки шаблонов

**Зачем.** Шаблон договора — это Google Doc, в который по тексту расставлены
вставки `{{selling_price}}` и условия `{{#if …}}{{/if}}`. Расставляет их не сайт,
а скрипты из репозитория (`scripts/markup-*.mjs`): они открывают документ через
Google API и вносят по 170–185 правок. Этими же скриптами собираются папки
с тестовыми договорами на все сценарии — те, что отправляли на проверку глазами.

Ходят скрипты в Google **не** под аккаунтом сайта и не под тем, кто сидит
за компьютером, а под отдельным аккаунтом-«ботом» с долгим токеном. Токен лежит
в `.env.local` и в репозиторий не попадает, поэтому новому владельцу его
не передают — он выпускает свой.

**6.1. Выбрать аккаунт бота.** Это обычный Google-аккаунт — можно свой рабочий.
Ему нужен доступ **на редактирование** к шаблонам, папке «MOU» и таблице,
иначе скрипты упадут с ошибкой прав.

**6.2. Создать для него OAuth-клиент** (отдельный от того, через который люди
входят на сайт): Google Cloud → Credentials → Create credentials →
OAuth client ID → тип **Desktop app**. Скопировать Client ID и secret.

**6.3. Вписать в `.env.local`:**

```
GOOGLE_BOT_CLIENT_ID=...
GOOGLE_BOT_CLIENT_SECRET=...
```

**6.4. Выдать токен:**

```bash
node scripts/google-auth.mjs
```

Скрипт напечатает ссылку `AUTH_URL: https://accounts.google.com/…` и будет ждать
до 5 минут. Ссылку открыть в браузере, выбрать аккаунт бота, на экране
«Google не проверил это приложение» нажать «Дополнительные настройки» →
«Перейти (небезопасно)», отметить **все** галочки прав (Документы, Диск, Таблицы),
«Продолжить». Во вкладке появится «Готово, можно закрывать», а скрипт сам допишет
в `.env.local` строку `GOOGLE_BOT_REFRESH_TOKEN=…`.

**6.5. Срок жизни.** Пока OAuth consent screen в режиме **Testing**, токен живёт
**7 дней**. Ошибка `invalid_grant` в любом скрипте означает ровно это: прогнать
п. 6.4 заново. Чтобы не перевыпускать каждую неделю — опубликовать consent screen
(Publishing status → Publish app) или держать аккаунты в Google Workspace
и поставить тип Internal.

**6.6. Как этим пользоваться.** Разметка нового шаблона — всегда сначала
на копии-черновике:

```bash
node scripts/markup-ready-mortgage-cash.mjs            # черновик, оригинал не трогается
node scripts/markup-ready-mortgage-cash.mjs --original # боевой шаблон, бэкап делается сам
```

Разметка **неидемпотентна**: второй прогон по уже размеченному документу его сломает.
После прогона по оригиналу — восстановить начертание:
`node scripts/fix-bold.mjs <ID шаблона> <ID бэкапа>`. Порядок работы с шаблоном
целиком и ID всех документов — в `docs/state.md`.
